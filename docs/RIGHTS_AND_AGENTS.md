# Права агента: универсальный агент и личные ассистенты

Руководство для администраторов. Здесь описано, **с чьими правами** работает агент в каждом канале, какие риски это несёт и как настроить личного ассистента для сотрудника.

## Два вида агентов

| | **Универсальный агент** | **Личный ассистент сотрудника** |
|---|---|---|
| Чьи права | свои: сервисная учётка «ИИ-агент», вебхук `BITRIX_WEBHOOK_URL` | **права самого сотрудника**: вебхук, созданный от его имени |
| От чьего имени действия | от «ИИ-агента» | от сотрудника: комментарии, задачи, изменения, согласования |
| Что видит | всё, что разрешено сервисной учётке | ровно то, что видит сотрудник в Битрикс24 |
| Память | история диалогов | история диалогов + **личная память** о сотруднике: стиль общения, роль, клиенты, коллеги, привычки |
| Где работает | групповые чаты и чаты объектов, таймлайн, автопомощь, участие в БП, MCP по умолчанию | личный чат с ботом «ИИ-агент» или отдельный скрытый бот сотрудника, MCP `--as` |
| Для чего | бизнес-процессы, общие сценарии, автоматизация | персональная работа: «мои сделки», письма, документы, задачи — с правами сотрудника |

### Какой агент отвечает в каждом канале

| Канал | Кто отвечает и с чьими правами |
|---|---|
| Личный чат с ботом «ИИ-агент» | зависит от `PRIVATE_CHAT_MODE` (см. ниже) |
| Личный бот сотрудника (`own_bot = true`) | всегда личный ассистент, с правами владельца; другим сотрудникам бот отказывает |
| Групповой чат, чат объекта | универсальный агент |
| @упоминание в таймлайне, отслеживание объекта | универсальный агент |
| Автопомощь по письмам и файлам | универсальный агент, только чтение |
| Задания бизнес-процессов | универсальный агент, только чтение при изучении документа |
| `b24agent mcp` | универсальный агент |
| `b24agent mcp --as 15` | личный ассистент сотрудника 15 |

Режим личного чата задаёт `PRIVATE_CHAT_MODE`:

| Значение | Поведение |
|---|---|
| `personal` (по умолчанию) | если у сотрудника есть личный ассистент, работает он (права и память сотрудника); иначе универсальный агент |
| `personal_only` | только личный ассистент; сотрудник без личного ассистента получает отказ. **Самый безопасный режим:** через личный чат никто не получит данные сверх своих прав |
| `service` | всегда универсальный агент (прежнее поведение) |

Узнать, кто сейчас отвечает, сотрудник может командой `/whoami`.

## Риски универсального агента и как их снизить

Универсальный агент **не проверяет права собеседника**: в Битрикс24 нет REST-метода «видит ли пользователь X эту сделку». Если сервисной учётке доступно больше, чем сотруднику, сотрудник может получить через агента чужие данные. Так возможно в групповом чате, в таймлайне, а при `PRIVATE_CHAT_MODE=service` — и в личном чате.

Что делать:
1. **Минимальные права сервисной учётки.** Дайте ей доступ только к тем воронкам, смарт-процессам и разделам, которые можно показывать всем пользователям агента и которые нужны для БП и автопомощи. Конфиденциальные разделы (зарплаты, кадры, руководство) не открывайте.
2. **`PRIVATE_CHAT_MODE=personal_only`** — личная работа идёт только через личных ассистентов с правами сотрудников.
3. **`AGENT_ALLOWED_USERS`** — круг сотрудников, которым агент вообще отвечает. Владельцы личных ассистентов допускаются автоматически.
4. **`AGENT_ALLOW_WRITE=false`** и **`TOOLS_DISABLED`** — запрет изменений и отдельных действий.
5. **Аудит.** Все действия универсального агента записываются от сервисной учётки, их видно в истории объектов и в журнале событий.

## Настройка личного ассистента

### 1. Вебхук сотрудника

Вебхук должен быть создан **самим сотрудником** в его учётной записи. Код вебхука видит только создатель, а если администратор отредактирует чужой вебхук, владельцем станет администратор.

1. Разрешите сотруднику создавать вебхуки: Настройки → Безопасность → Интеграции Битрикс24 → «Кому разрешить создавать входящие вебхуки».
2. Сотрудник открывает Разработчикам → Другое → Входящий вебхук и выдаёт права `crm, task, user, im, department, sonet_group, calendar, bizproc, lists, disk`. Право `imbot` не нужно: бот работает через сервисный вебхук.
3. Сотрудник передаёт URL администратору **защищённым способом**: не в чате и не по почте. URL — это ключ с правами сотрудника.

### 2. Конфигурация

Скопируйте [`personal_agents.example.toml`](../personal_agents.example.toml) в `personal_agents.toml`. Файл в `.gitignore`, в репозиторий он не попадает. Пример:

```toml
[[agent]]
user_id = 15                      # ID сотрудника в Битрикс24
name = "Ассистент Анны"
webhook_env = "PA_15_WEBHOOK"     # URL вебхука — в переменной окружения (рекомендуется)
own_bot = false                   # true — отдельный скрытый бот только для этого сотрудника
allow_write = true                # false — ассистент только читает
memory = true                     # личная память о сотруднике
prompt = "Обращайся на «ты». Отвечай кратко, списком."   # или prompt_file = "prompts/anna.md"
tools_disabled = ["bp_start"]
```

В `.env` или в окружении службы: `PA_15_WEBHOOK=https://portal.company.ru/rest/15/xxxxxxxx/`.

### 3. Проверка и запуск

```bash
uv run b24agent personal            # вебхук работает и принадлежит этому сотруднику, режим, память
uv run b24agent ask --as 15 "какие у меня сделки в работе?"
uv run b24agent setup               # регистрирует личных ботов (own_bot) и присылает сотруднику приветствие
uv run b24agent serve
```

Агент **проверяет владельца вебхука**: ID в URL и ответ метода `profile` должны совпадать с `user_id`. Вебхук другого пользователя не будет принят, и такой профиль отключается с ошибкой в логе.

### Где сотрудник общается с ассистентом

- **`own_bot = false`** — в личном чате с общим ботом «ИИ-агент» (при `PRIVATE_CHAT_MODE=personal` или `personal_only`).
- **`own_bot = true`** — отдельный бот с именем ассистента («Ассистент Анны»). Бот скрыт из поиска (`isHidden`) и сам пишет владельцу первое сообщение после `setup`. Другим сотрудникам он не отвечает.

История личного ассистента общая для обоих вариантов.

## Личная память

- Ассистент сам запоминает **устойчивые предпочтения и факты**: как обращаться, стиль и длину ответов, роль сотрудника, ключевых клиентов и проекты, коллег и их роли, привычные сроки. Для этого есть инструменты `memory_save`, `memory_list` и `memory_forget`. Сотрудник может попросить явно: «запомни, что отчёт я сдаю по пятницам».
- Память подставляется в каждый разговор с владельцем. Её видит только личный ассистент этого сотрудника, у универсального агента памяти нет.
- **Команды:** `/memory` — что ассистент помнит, «забудь [номер]» — удалить заметку, `/forget` — очистить всю память.
- **Хранение:** локально в `DATA_DIR/agent.sqlite3` (таблица `user_memory`), в Битрикс24 память не пишется. До `PERSONAL_MEMORY_MAX` заметок (по умолчанию 50, старые вытесняются), не длиннее 500 символов. Похожее на пароли и токены не сохраняется.
- **История диалога** личного ассистента длиннее: `PERSONAL_HISTORY`, по умолчанию 40 реплик.

## Увольнение и смена прав

- Права ассистента меняются **автоматически** вместе с правами сотрудника в Битрикс24.
- При увольнении:
  - удалите запись из `personal_agents.toml` и переменную с вебхуком;
  - удалите вебхук сотрудника на портале. Если при увольнении выбрать «Сохранить интеграции и уволить», вебхук перейдёт системному пользователю и **продолжит работать**;
  - очистите память: удалите строки `user_memory` с этим `user_id` или попросите сотрудника выполнить `/forget` до ухода.
- Личного бота удалите командой `b24agent unregister`, либо оставьте: без профиля он отвечает отказом.

## Почему агент работает снаружи Битрикс24

**Исходящие вебхуки** права пользователя не дают. Они только сообщают о событии: в коробке такие события идут через облачную очередь Битрикс24, а токен события не даёт действовать от имени пользователя. Для закрытого контура и для прав они не подходят.

**Встроить агента в Битрикс24** можно тремя способами:

| Вариант | Что даёт | Ограничения |
|---|---|---|
| **Локальное приложение (OAuth)** | токен каждого сотрудника, работа с его правами без ручной раздачи вебхуков, встройки в интерфейс (вкладка в карточке, кнопка в чате) | в коробке токены выдаются через `oauth.bitrix24.tech`, а это внешний доступ, что для закрытого контура обычно неприемлемо. Есть обход — свой провайдер авторизации, PHP-доработка |
| **Свой модуль на коробке (PHP, `local/modules`)** | собственные REST-методы, которые выполняют действия **от имени заданного пользователя с проверкой его прав** штатными механизмами Битрикс24. Тогда хватит одного сервисного вебхука, а права проверяет сам портал | нужна PHP-разработка под вашу версию коробки и её сопровождение при обновлениях |
| **Текущая схема: агент снаружи + вебхуки сотрудников** | работает без доработок портала, права проверяет сам Битрикс24, есть личная память | вебхуки сотрудников нужно выдавать и отзывать вручную |

LLM в любом варианте работает отдельным сервисом. Поэтому «мозг» агента остаётся снаружи, а внутрь Битрикс24 можно перенести только его «руки», то есть проверку прав и выполнение действий. Для пилота и десятков личных ассистентов подходит текущая схема. При масштабировании на сотни сотрудников стоит перейти на модуль с методами «от имени пользователя»: агент сможет работать с правами любого сотрудника без личных вебхуков.

## Настройки

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PERSONAL_AGENTS_FILE` | `personal_agents.toml` | файл с личными ассистентами |
| `PRIVATE_CHAT_MODE` | `personal` | `personal` / `personal_only` / `service`: чьи права в личном чате с общим ботом |
| `PERSONAL_MEMORY_MAX` | `50` | заметок личной памяти на сотрудника |
| `PERSONAL_HISTORY` | `40` | реплик истории диалога личного ассистента |
| `AGENT_ALLOWED_USERS` | — | кому отвечает агент; владельцы личных ассистентов допускаются всегда |
