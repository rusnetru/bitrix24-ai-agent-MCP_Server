# Что это и как устроено

`b24agent` — это ИИ-агент и MCP-сервер для **коробочного Битрикс24** в закрытом корпоративном контуре. Он выполняет две роли, и обе используют один и тот же набор инструментов.

1. **Встроенный агент (чат-бот).** Сотрудник пишет боту в мессенджер или упоминает его в таймлайне объекта CRM. Агент вызывает корпоративную LLM через LiteLLM. Модель решает, какие инструменты вызвать, агент выполняет их через REST портала и отвечает в том же канале.
2. **MCP-сервер (`b24agent mcp`).** Те же инструменты по протоколу Model Context Protocol (stdio) для любых MCP-клиентов: Claude Desktop, Cursor, внутренние агентные платформы.

```
                ┌───────────────────────── закрытый контур ─────────────────────────┐
 Сотрудник ──►  │  Битрикс24 (коробка)                                              │
  чат / @упом.  │    ▲   ▲                                                          │
                │    │   │ REST: входящий вебхук (/rest/{user}/{code}/...)          │
                │    │   │       REST 3.0 (/rest/api/{user}/{code}/...)             │
                │    │   │                                                          │
                │  imbot.v2.Event.get (fetch)   ◄──── b24agent serve ────► LiteLLM ──► Qwen │
                │  crm.item.list / timeline         │  агент + инструменты          │
                │                                    └── b24agent mcp ◄── MCP-клиенты │
                └───────────────────────────────────────────────────────────────────┘
```

Все соединения исходящие: от агента к порталу и от агента к LiteLLM. Портал не обязан уметь достучаться до агента: чат-бот работает в режиме **fetch**, а таймлайн читается опросом.

## Что агент «видит» и умеет

| Область | Что доступно | REST под капотом |
|---|---|---|
| CRM: сделки, лиды, контакты, компании, предложения, счета | поиск, список с фильтрами, карточка с подписанными полями и стадиями, создание, изменение, смена стадии, связи, история стадий, дела | `crm.item.*`, `crm.status.list`, `crm.category.list`, `crm.duplicate.findbycomm`, `crm.{lead,contact,company}.*` (телефоны и email), `crm.stagehistory.list`, `crm.activity.todo.add` |
| **Смарт-процессы** (любые, по entityTypeId или названию) | то же, что для сделок, плюс справочник типов, воронки и стадии, пользовательские поля с вариантами списков | `crm.type.list`, `crm.item.*`, `crm.item.fields`, `crm.status.list` (`DYNAMIC_<id>_STAGE_<cat>`) |
| **Письма** в таймлайне | список писем объекта, полный текст, адресаты, вложения | `crm.activity.list` (`TYPE_ID=4`, `PROVIDER_ID=CRM_EMAIL`), `crm.activity.get` |
| **Файлы объекта** (Диск) | все файлы: поля «Файл» и «Файл (Диск)», вложения комментариев, писем и дел; чтение содержимого (PDF, DOCX, XLSX, PPTX, ODT, RTF, TXT, CSV, HTML, EML), чтение частями, кэш | `crm.item.get` (`urlMachine`), `disk.attachedObject.get`, `disk.file.get` → `DOWNLOAD_URL`, `crm.timeline.comment.list` (`FILES`) |
| Таймлайн | чтение комментариев и дел; ответы комментарием; отслеживание объекта | `crm.timeline.comment.list/get/add`, `crm.activity.list` |
| Задачи | поиск (мои, по объекту CRM, по фильтрам), карточка с чек-листом и привязками, создание с привязкой к CRM и смарт-процессу, изменение, смена статуса, комментарии | `tasks.task.*`, `task.commentitem.*` |
| Сотрудники и оргструктура | поиск сотрудника и его ID, подразделения, состав подразделения, рабочие группы и проекты | `user.search`, `user.get`, `department.get`, `socialnetwork.api.workgroup.list` |
| Календарь | события, занятость коллег, создание встречи | `calendar.event.get/add`, `calendar.accessibility.get`, `calendar.section.get` |
| Бизнес-процессы | мои задания на согласование, согласование и отклонение, шаблоны, запуск БП (нужен админ) | `bizproc.task.list/complete`, `bizproc.workflow.template.list`, `bizproc.workflow.start` |
| Универсальные списки | списки, поля, элементы, добавление элемента | `lists.get`, `lists.field.get`, `lists.element.get/add` |
| Чаты | личный чат с ботом, групповые чаты (по @упоминанию), привязка чата к объекту, создание чата по объекту | `imbot.v2.*` (или `imbot.*` v1) |
| Всё остальное | любой метод REST по политике безопасности | `bitrix_call` (REST 2 и 3.0), `bitrix_method_info` (`method.get`) |

Полный актуальный список с описаниями печатает `b24agent tools`. Команда `b24agent tools --json` дополнительно выводит JSON Schema параметров.

## Каналы общения

**Личный чат.** Сотрудник находит бота в мессенджере и пишет ему. Контекст: кто спрашивает (ID пользователя), история диалога (`AGENT_HISTORY` последних реплик).

**Групповой чат.** Бот реагирует на @упоминание (тип `bot`). Чтобы бот видел все сообщения в своих чатах, задайте `BOT_TYPE=supervisor`.

**Чат объекта.** Привязать чат к объекту можно тремя способами:

- `chat_bind_entity`: «привяжи этот чат к проекту 15»;
- `chat_create_for_entity`: «создай чат по сделке 123»; бот создаёт чат, добавляет ответственного и автора запроса, оставляет ссылку в таймлайне;
- штатный чат CRM-карточки: привязка определяется по `ENTITY_TYPE=CRM`, `ENTITY_ID=DEAL|123` или `DYNAMIC_1038|5`.

После привязки в системный промпт попадает сводка объекта, и «он», «эта сделка» понимаются без ID.

**Таймлайн.** Агент отвечает в двух случаях:
- в комментарии упомянули бота, пользователя вебхука или ID из `TIMELINE_MENTION_IDS`;
- объект поставлен на отслеживание (`timeline_watch`), и тогда агент отвечает на все новые комментарии.

Ответ публикуется комментарием с упоминанием автора. Автор комментария — **пользователь вебхука**: `crm.timeline.comment.add` не принимает автора. Поэтому вебхук создают от сервисной учётки, например «ИИ-агент».

## Автопомощь по письмам и файлам

`AUTO_ASSIST_TYPES=1038,deal` включает автопомощь. Раз в `AUTO_ASSIST_INTERVAL` секунд агент проходит по элементам этих типов с новой активностью (`lastActivityTime`) и ищет:
- новые **входящие письма** (`AUTO_ASSIST_ON=email`);
- новые **файлы в комментариях** таймлайна, кроме своих (`AUTO_ASSIST_ON=file`).

По каждой находке агент запускается в режиме **только чтения**: инструменты изменения ему не передаются. Он читает письмо и вложения, сверяется с карточкой объекта и готовит справку. Состав справки задаётся `AUTO_ASSIST_PROMPT_FILE`, по умолчанию это:
- суть;
- что просят: сроки, суммы, условия;
- риски;
- следующие шаги;
- черновик ответа.

Справка публикуется комментарием «ИИ-помощник» в таймлайне и/или личным сообщением ответственному от бота (`AUTO_ASSIST_TARGET=timeline,chat`). Она сохраняется в историю разговора таймлайна, поэтому можно сразу спросить «@ИИ-агент а что со штрафами?». Повторно одно и то же письмо или файл не обрабатывается. Лимит — `AUTO_ASSIST_MAX` справок за один проход.

## Участник бизнес-процессов

`BP_AGENT=true`: агент опрашивает свои задания (`bizproc.task.list`, пользователь — владелец вебхука). По каждому заданию он:
1. собирает инструкцию из описания задания, тип действия, поля для заполнения и сводку документа;
2. изучает документ читающими инструментами;
3. возвращает JSON-решение.

Код проверяет решение: оно должно подходить к типу задания и к разрешённым решениям (`BP_AGENT_DECISIONS`), обязательные поля должны быть заполнены, значения списков — существовать, уверенность — не ниже `BP_MIN_CONFIDENCE`. Затем код выполняет `bizproc.task.complete` с комментарием «ИИ-агент: …». Всё, что не прошло проверку, передаётся человеку (`BP_AGENT_ESCALATE_TO`): ему приходит сообщение, и задание делегируется. Подробности — в [BP_PARTICIPANT.md](BP_PARTICIPANT.md). Модуль: `b24agent/bp_participant.py`.

## Как события доходят до агента

| Источник | Режим | Нужен входящий доступ к агенту? |
|---|---|---|
| Сообщения боту | `BOT_API=v2`, `BOT_EVENT_MODE=fetch`: агент опрашивает `imbot.v2.Event.get` каждые `BOT_POLL_INTERVAL` секунд | **нет** |
| Сообщения боту | `BOT_EVENT_MODE=webhook` (v2) или `BOT_API=v1`: портал делает POST на `PUBLIC_URL/bitrix/events?secret=…` | да |
| Комментарии в объектах на отслеживании | `TIMELINE_POLL_INTERVAL=30`: опрос `crm.timeline.comment.list` по каждому объекту | нет |
| @упоминания в таймлайне любых объектов выбранных типов | `TIMELINE_SCAN_TYPES=deal,1038`: опрос `crm.item.list` по `lastActivityTime`, затем комментарии найденных элементов | нет |
| `ONCRMTIMELINECOMMENTADD` | исходящий вебхук портала на `/bitrix/events` | да; в коробке доставка идёт через облачную очередь Битрикс24, поэтому для закрытого контура не подходит |

Через входящий вебхук **нельзя** подписаться на события: `event.bind` возвращает `WRONG_AUTH_TYPE`. Офлайн-события доступны только приложениям. Поэтому в закрытом контуре используются fetch и опрос.

### Жизненный цикл запроса в чате

1. `fetch_loop` получает `ONIMBOTV2MESSAGEADD`, затем `parse_v2` превращает событие в `Incoming`.
2. `on_message` проверяет:
   - дедупликацию по ID сообщения;
   - доступ (`AGENT_ALLOWED_USERS`);
   - служебные команды `/help`, `/clear`, `/context`;
   - привязку чата к объекту.
3. `Agent.run` собирает системный промпт. В него входят:
   - дата;
   - кто спрашивает;
   - список смарт-процессов портала;
   - контекст объекта;
   - дополнительные инструкции из `AGENT_PROMPT_FILE`.

   К промпту добавляется история диалога.
4. Цикл до `AGENT_MAX_STEPS` шагов:
   - модель вызывает инструменты;
   - `Toolbox.execute` выполняет их с проверками (запись, `bot_only`, отключённые) и обрезает длинный результат;
   - результат возвращается модели.
5. Ответ переводится из Markdown в BB-коды и отправляется через `imbot.v2.Chat.Message.send`, история сохраняется.

## Безопасность

- **Права агента равны правам пользователя вебхука.** Создавайте вебхук от сервисной учётки с минимально нужными правами CRM и задач и с нужными scope.
- `AGENT_ALLOW_WRITE=false` включает режим только чтения: изменяющие инструменты не передаются модели.
- `AGENT_ALLOWED_USERS` ограничивает круг сотрудников, которые могут общаться с агентом.
- `TOOLS_DISABLED` точечно отключает инструменты.
- У `bitrix_call` своя политика доступа:
  - по умолчанию только читающие методы;
  - `BITRIX_CALL=full` разрешает запись, но список опасных методов остаётся закрыт (`*.delete`, `event.*`, `imbot.*`, `user.update`, `*.userfield.*` и т. д.);
  - через `batch` вызывать методы нельзя.
- `EVENT_SECRET` защищает HTTP-приёмник в push-режиме.
- Секреты лежат только в `.env`: вебхук, `LLM_API_KEY`, `BOT_TOKEN`. Если `BOT_TOKEN` не задан, он генерируется и хранится в `data/agent.sqlite3`.
- Агент не логирует URL вебхука. Не включайте `LOG_LEVEL=DEBUG` в продуктиве: в этом режиме пишутся тела событий.
